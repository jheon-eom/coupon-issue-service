** v2 테스트 목적 **
- v1에서 발생한 쿠폰 초과 발급 문제를 막기 위해 DB 동시성 제어(비관적 락) 적용
- 목표: 쿠폰 발급 수량을 정확히 500개로 제한

** v2 성능 결과 (출처: performance.png) **
- checks_total: 37,212
- checks_succeeded: 1.34% (500 / 37,212)
- checks_failed: 98.65% (36,712 / 37,212)
- http_req_failed: 98.65% (36,712 / 37,212)
- http_req_duration(avg): 10.04s
- http_req_duration(median): 9.19s
- http_req_duration(p90/p95): 21.22s / 28.63s
- expected_response(true) 기준 latency:
  - avg 737.53ms, median 759.65ms, p95 1.33s
- dropped_iterations: 88,429

** 정합성 결과 **
- 실제 성공 응답(200)은 정확히 500건으로 확인
- 쿠폰 제한(500개)과 발급 결과가 일치하여, v1의 초과 발급 문제는 해결됨

** v1 vs v2 비교 **
- 정합성:
  - v1: 쿠폰 500개 제한인데 4,990개 발급(초과 발급)
  - v2: 정확히 500개 발급(정합성 확보)
- 성공률(테스트 기준):
  - v1: 14.98% (4,990 / 33,301)
  - v2: 1.34% (500 / 37,212)
  - 차이 해석: v2는 한도를 지키기 때문에 성공 건수가 500에서 더 늘지 않음
- 평균 응답시간:
  - v1: 9.28s
  - v2: 10.04s
  - v2가 약 0.76s 느림

** 성능 차이 원인 분석 **
1. DB 비관적 락으로 인한 직렬화
- v2는 쿠폰 row를 잠그고 순차 처리하므로, 동시 요청이 많을수록 대기 시간이 증가

2. 동일한 트래픽 규모에서 성공 상한이 500으로 고정
- 테스트 트래픽은 수만 건인데 성공 가능 건수는 500건으로 제한됨
- 따라서 나머지 요청은 실패로 집계되어 성공률이 크게 하락

3. 락 대기 + 재고 소진 이후 실패 응답 집중
- 재고가 소진된 뒤에도 많은 요청이 유입되어 실패 응답이 대량 발생
- `http_req_failed 98.65%`, `dropped_iterations 88,429`가 이를 뒷받침

4. 핵심 해석
- v2는 “성공률”을 높이는 버전이 아니라, “정합성(초과 발급 방지)”을 우선 달성한 버전
- 즉, 성능 저하는 동시성 제어 강화에 따른 trade-off로 해석하는 것이 타당
