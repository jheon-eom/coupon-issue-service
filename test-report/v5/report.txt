** v5 테스트 목적 **
- v4 대비 HTTP 요청 처리량을 추가로 끌어올리고, 응답 지연/실패율을 더 낮추는 것이 목표
- v5에서는 요청 핫패스에서 Kafka 직접 전송을 제거하고, Redis 원자 처리(카운터+pending enqueue) 후 즉시 응답
- Kafka 발행은 별도 릴레이 워커가 처리하고, 서버 톰캣 동시성 설정을 튜닝해 처리량을 확장

** 결론: v5는 v4 대비 성능이 더 개선됨 **
- 처리량이 2배 이상 증가했고, 실패율은 0%로 감소
- 평균 및 tail latency(p90/p95)가 크게 줄어 고부하 안정성이 더 좋아짐

** v5 개선 원인 분석 (v4 대비) **
1. 요청 핫패스의 동기 의존 제거
- v4는 요청 처리 중 Kafka 전송 대기 구간(동기 전송 대기)이 포함될 수 있었음
- v5는 Redis Lua 원자 연산으로 카운트+큐 적재만 수행하고 즉시 응답
- 네트워크 I/O(Kafka)를 요청 경로에서 분리해 avg/p90/p95 개선

2. 비동기 발행의 역할 분리
- Kafka 발행을 릴레이 워커로 분리하면서 API 스레드가 브로커 상태/지연에 직접 묶이지 않음
- 발행 실패는 재시도 큐로 흡수되어 API 실패율이 감소

3. 톰캣 동시성 설정 튜닝
- threads/accept-count/max-connections 확대로 동시 요청 수용 능력 증가
- 고부하에서 큐 대기/거절 감소에 기여해 처리량 상승 및 dropped_iterations 감소

4. Redis 원자 처리의 짧은 임계 구간
- 카운터 증가와 pending 저장을 단일 원자 스크립트로 처리하여 경합 시에도 예측 가능한 짧은 처리 경로 유지
- lock chain이 길어지지 않아 tail latency가 개선

** 해석 시 유의사항 **
- v5는 비동기 발행 구조라서 본 결과는 주로 "API 응답 성능"을 반영
- 발행 보장 품질 평가는 별도 지표(릴레이 retry 큐 길이, relay failed 큐, Kafka lag)로 함께 확인 필요
- v4/v5 비교의 정확성은 동일 부하 스크립트/동일 인프라 조건을 전제로 함
